Curriculum Architecture Overview

Four tracks. Two experience levels. Two time horizons. One unified goal: competent AI engineers.

Track A — Experienced Engineers

For students with backend or fullstack development experience. Proficiency in at least one language (Python, Node.js, Go, Java, etc.), experience with APIs, databases, and Git assumed. The programming fundamentals onboarding is condensed from weeks to days, freeing the entire track for deep AI content.

PREREQ: Backend or Fullstack experience

Track B — Zero Experience

For students with no coding background. CS, math, or science students who've never written a line of code. The first quarter of the program is dedicated to Python from absolute scratch, command-line fluency, and tooling. The AI engineering content then builds on this foundation. Outcome is more applied/LLM-engineering focused than Track A.

PREREQ: Basic computer literacy only
80/20 Principle Applied: Both tracks ruthlessly prioritize the skills that account for the majority of real AI engineering work — Python, LLM APIs, embeddings, RAG, agents, and deployment — over exhaustive coverage of classical ML theory. Classical ML (Weeks 3–4 in Track A) is taught for conceptual literacy and interview preparedness, not as the primary output of the program.

The 3-month track makes a deliberate trade-off: it skips ML theory, classical algorithms, and DL foundations entirely. Instead it goes Python → Python for AI tools → LLM APIs → RAG → Agents → Deploy. Auditing System

Per-assessment-type auditing strategy, escalation tiers, and integrity mechanisms.

The platform's Audit entity carries conference_link (for raid oral defences), AuditQuestion checklists (configurable per context), and a peer_audit_required flag on quests and raids. The auditing strategy below maps to these fields.

Code Quest Auditing

T1
Automated Test Cases (100% of submissions)
All code quests have test_cases JSON. Submission triggers automated runner against defined input/output pairs. Pass/fail determined by test coverage threshold (default: 100% pass rate on public tests, hidden tests vary).
T2
AI-Assisted Code Review (all passing submissions)
LLM reviews code for: style alignment, potential plagiarism indicators (unusual similarity to other submissions), hardcoded test outputs, inappropriate shortcuts. Flags suspicious submissions for T3.
T3
Peer Audit (for allows_peer_audit = true quests)
Assigned reviewer (anonymous) checks: does the code actually solve the problem? Is it the student's own work? Uses AuditQuestion checklist. Reviewer has 48 hours. Dispute resolution goes to T4.
T4
Instructor Review (flagged only, <5% of submissions)
Manual review by instructor. May trigger a live explanation session (verbal defense via conference_link). Outcome: pass / fail / retry.

Notebook Quest Auditing

T1
Structure Validation (automated)
Check: notebook is committed to Gitea, all required cells exist, outputs are present (not cleared), file naming convention matches repository_naming_convention.
T2
AI Output Review (automated + AI-assisted)
Specific cell outputs (model accuracy, final metrics, visualizations) are extracted and checked against expected ranges. AI reviews narrative cells for coherence and correctness.
T3
Instructor Spot-Check (15% random + all flagged)
Instructor reviews full notebook. Checks that analysis is genuine, conclusions are supported by the data, and there's no copy-paste of outputs without understanding.

MCQ Quest & Checkpoint Auditing

T1
Fully Automated Scoring
Instant scoring on submission. Results locked on submit (no editing after). Score history kept per attempt.
T2
Behavioral Analytics
Time-per-question tracking. Flag if: all questions answered in under 60s total, answer pattern matches another student identically, session IP/device anomalies. Flagged → T3.
T3
Randomized Question Banks + Re-sit Protocol
Different students see different questions from the same bank. If cheating is suspected, student is required to re-take under proctored conditions (physical or screen-share). Outcome determines official score.

Essay & Short Answer Auditing

T1
AI Rubric Scoring (all submissions)
LLM grades against a pre-defined rubric with criteria and weights. Returns a score + criterion-level breakdown. This score is the starting score.
T2
Blind Peer Review (2 peers per essay)
Two cohort members grade the same essay independently using AuditQuestion checklist. Reviewers don't see each other's scores. Final score = weighted avg of AI score + peer 1 + peer 2 (configurable weights per quest). Outlier resolution goes to T3.
T3
Instructor Adjudication (outliers + disputes)
Triggered when: peer scores diverge by >30%, student disputes the score, or AI flagged the essay as potentially AI-generated. Instructor makes final call.
T4
AI-generated Content Detection
All essays screened for LLM-generation patterns. High-probability AI-generated submissions require a live verbal follow-up (explain your argument verbally). Confirmed AI-generated work = 0 score + warning.

Checkpoint Auditing

T1
Automated Scoring (MCQ + code portions)
MCQ: instant scoring. Code tasks: automated test runners. Results available within 1 hour of submission close.
T2
Instructor Review (essay + short answer)
All essay portions reviewed by instructor within 48 hours. Rubric-based, documented scoring. Appeals window of 72 hours after results.
T3
Final Checkpoint — Oral Component
Oral exam scored live by 2 instructors. AuditQuestion checklist used. Recording kept for 30 days. Pass requires ≥70% on written + oral combined.

Raid Auditing

T1
Automated Repo Tests (all raids with code)
Test suite runs against the shared Gitea repo. Checks: all tests pass, deployment URL returns 200, required files present, commit history shows multiple contributors.
T2
Contribution Analysis
Git commit history analyzed: each member must have a meaningful commit ratio. Flags groups where one person did >80% of commits. Flagged groups → T4.
T3
Peer Contribution Rating (within group)
Each group member rates all other members' contribution (1–5 scale + short text). Aggregated privately. Severe outliers (member rated 1 by all others) → instructor review.
T4
Code Explanation Oral Audit (all Standard/Extended Raids)
All members are called into a video session (conference_link on Audit entity). Each member is asked to explain 2–3 random parts of the codebase — including parts they didn't write. Inability to explain = group fail. Session recorded. AuditQuestion checklist used.
Integrity Policy Summary
Violation Type Detection Method First Offense Second Offense
Hardcoded test outputs in code quest AI code review (T2) + hidden test cases Quest invalidated, 72hr cooldown, re-attempt required Subject-level review + formal warning
Code copying between students Similarity detection (T2) Both students: quest invalidated + oral explanation required Program probation
AI-generated essay submission AI detection + verbal follow-up Score = 0, must resubmit with verified work Program suspension review
Raid free-riding (contribution <15%) Git analysis (T2) + peer rating (T3) Individual raid fail (group may still pass), quest re-assigned Group disbanded, solo re-do
Inability to explain code in oral audit Oral audit (T4) Entire group fails the raid, must redo Individual academic review
Checkpoint cheating (copied answers) Behavioral analytics (T2) Proctored re-sit required (physical) Formal academic misconduct process
Auditing Philosophy: The goal is not to catch cheaters — it's to make authentic learning the path of least resistance. Automated tests are intentionally designed so that gaming them (e.g. hardcoded outputs) is harder than solving the problem. Oral components at checkpoints and raids make knowledge internalization non-negotiable. The peer audit system is as much a teaching tool (reviewers learn by reviewing) as an integrity mechanism.
